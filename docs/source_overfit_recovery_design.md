## Execution and records

Use one detached Python supervisor, launched from a separate hidden PowerShell process with `Start-Process -WindowStyle Hidden`, explicit interpreter/working directory and stdout/stderr files. It survives this conversation and agent-service rate limits. Do not attach its lifetime to an exec-tool session. A readable status command reports job/worker PIDs, current committed step, heartbeat, outcome and log paths. A second launch attaches/reports an existing live job rather than starting a competing worker. Use a process-lifetime OS file lock and PID plus creation-time identity; never kill an unrelated PID. Keep terminal/Codex and essential Windows/VPN alive. Close authorized unused apps only as needed for the registered hardware gate.

The supervisor owns one job RunRecord in `runs/source-overfit-20261017-recoverable-v2`. It starts at most three worker processes sequentially: initial segment0 plus at most2 automatic recoveries from a verified committed checkpoint. Each worker owns a separate `segment-000`, `segment-001` or `segment-002` RunRecord, logs and artifacts. A crashed segment's files are retained; never reopen/overwrite its logs or terminal. The job initial manifest resolves all settings before workers read task semantics/CUDA; each worker initial/access record precedes its own model/data access. Bind exact clean physical source, config/cohort/data/model/tokenizer/runtime/environment identities; recovery requires the same source commit and bytes, not a merely compatible descendant. Original base is freshly loaded from the pin on each worker, then learned/optimizer/scheduler/scaler=None/sampler/all RNG states restore through the existing checkpoint helper. Never initialize from the synthetic feasibility checkpoint.

Only interruption/process loss with no completed/failed scientific or invariant result can recover. Numerical divergence, OOM, identity/config/checkpoint corruption, gradient/frozen-weight/resume-invariant failure, completed NO_GO/PASS, exhausted total budget or recovery count are terminal; no reset/reseed/retuning. If no committed checkpoint exists, stop and preserve the initial failure rather than silently start fresh. A completed durable result may be sealed by the supervisor after a worker exits during finalization, but its summary/predictions/checkpoint and all gates must be independently hash-verified first; never infer PASS from exit0 or a stale status file.

No scheduled Windows startup task is added. The detached supervisor automatically recovers a lost worker while alive. If the supervisor/computer itself stops, rerunning the same launch command automatically discovers the committed cursor, verifies identities, and resumes within the remaining original budget. Report that boundary explicitly; do not claim a process can run through a machine shutdown or disk failure.

## Durable optimizer boundaries

Every completed **net** optimizer update is durably checkpointed before starting the next update. Save checkpoint0 before initial evaluation, and save metadata after a complete initial evaluation so recovery reuses its original CE/predictions. Existing complete checkpoint helpers write a new exclusive file, fsync and SHA-256; the recovery layer then writes an exclusive, fsynced stable-JSON metadata file binding checkpoint hash, all six identities, progress, phase and metrics, and atomically publishes a small cursor with both file hashes. A crash before cursor publication leaves the previous safe boundary plus preserved orphan files. No checkpoint can be selected by filename/mtime alone.

Within a live segment retain its newest two committed recovery checkpoints/metadata pairs, plus all registered96/192 checkpoints and the96→97 probe evidence. Delete only older positive rolling recovery pairs after the new cursor is durable and validated. Resolve every deletion path as an immediate registered recovery-directory child with an exact generated filename; reject links/reparse points and any escape. Never delete any artifact after its segment terminates. Thus interrupted segments preserve their latest two boundaries; at most three segments, about3.5GiB checkpoint storage rather than192 retained383MiB copies. Record hashes and retirement events for removed rolling versions; these are explicitly nonarchival rolling checkpoints, not complete artifact backups.

Cursor phases are `initial_evaluation_pending`, `training`, `resume_probe_pending`, `final_evaluation_pending`, `complete`. Metadata includes initial state hash/recipe and completed initial metric/prediction identity, current net progress, fixed checkpoint/probe identities, whether the intrinsic continuation check passed, and final result identity if complete. Saving/metadata/hashing must not consume the training/evaluation/global RNG streams. Loading strictly verifies exact schema, identities, hashes, shape/dtype/device and progress before mutation; no corrupt-cursor fallback that weakens verification.

At96 commit `resume_probe_pending`. The discarded97 probe does not publish a net recovery cursor. Restore96, rerun97 and verify the existing registered same-host tolerance before committing97 with the probe result. A crash during that pair resumes96 and repeats the pair; both interrupted partial paths remain recorded. After192 save the exact final checkpoint, publish `final_evaluation_pending`, evaluate the final3 using the same noise/policy, then durably publish `complete` binding final summary and predictions. Recovery from final-pending performs no training update. Completed initial/final evaluations are never used for new choices, and official quality denominators remain3 per checkpoint.

The no-loss contract is a durable optimizer boundary: an in-flight update not yet committed can be redone. Do not promise recovery of arithmetic that never reached durable storage. Fsync logs, hashes and the checkpoint/cursor transaction establish which boundary is safe. Report committed progress separately from observed physical work and any unobserved in-flight work when a process was killed.

If the old worker survives, attach and monitor it, without consuming another recovery or spawning any process. If worker ownership is locked but identity is missing/inconsistent, fail closed; never guess that an orphan exited. **Strict job-record reopen.** Add one private study-specific helper in the supervisor module, not a change to the pinned records foundation.
