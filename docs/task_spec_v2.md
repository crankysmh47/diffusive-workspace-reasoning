# Finite-domain composition task, v2 proposal

Date: 2026-10-08. Status: **prospective design only**. This document does not authorize implementation, generation, audit, or training. It versions the task-generation contract after the incomplete v1 suitability attempt; [task_spec.md](task_spec.md), [constraint_v1.json](../configs/tasks/constraint_v1.json), the v1 run, and its partial evidence remain frozen.

## Question and scope

The scientific question remains fixed-N exchangeable transfer: can one workspace/interface trained on source tasks transfer to unseen compositions of the same three known rules, without target-specific tuning? This proposal changes only candidate generation and prospective task eligibility. It does not add diffusion, variable slot count, new model families, or training. A passing task gate is necessary, not sufficient, for any later model comparison.

The v1 partial run stopped at 22,450 of 30,000 source attempts with `PermissionError [WinError 5]`; this was a Windows manifest-replacement interruption, not an exhausted attempt/resource cap. Source yielded 185 accepted groups; development and final were unattempted. Thus there is no measured zero target yield. Of the source structures seen, 51 signatures had no example sensitive to removal of one constraint. The observed n=3 equality triangle is demonstrably redundant under that test: deleting any edge leaves one solution. The old common-support result has empty target cohorts and cannot establish mismatch. These facts are retained unchanged; the generator proposal does not explain the original interruption.

## Frozen semantic and partition contract

The v1 grammar and model boundary remain byte-for-byte authoritative: schema `constraint-task-v1`; modulus 3 and domain `{0,1,2}`; `n` in 3–6; 2–8 distinct-operand constraints; 1–`n-2` givens; `eq`, `neq`, and `add_mod` with their v1 arities, operand symmetries, formulas, strict parser/verifier, independent exhaustive oracle, solver order and difficulty statistics. The prompt projection remains unchanged and contains only rules, task, and fixed answer-format instruction. Witnesses, solutions, identities, split labels, sensitivity evidence, and solver/audit fields are private metadata and must never enter model input.

Composition sets and use remain unchanged: source contains singleton profiles `{eq}`, `{neq}`, `{add_mod}`; development contains the three two-kind profiles; final contains `{eq,neq,add_mod}`. Preserve v1 canonical content/lineage/structure IDs and split hash domains/rules. Source content groups use 80/10/10 train/validation/test; development signatures use 80/20 validation/diagnostic-test, with diagnostic-test reporting-only; final signatures are used only for structural audit and untouched final evaluation after all rules and analysis are frozen. Final-target sampling and metrics are prohibited during the feasibility attempt.

## Versioned generation proposal

Implement as generator/config v2 with the same task schema and a new, explicit generator identity. Use root seed `20261007`; unsigned 64-bit root seed and candidate index; UTF-8/ASCII tokens; standard-library `random.Random`, initialized with `seed(..., version=2)`; no global RNG. For each candidate, derive its seed from SHA-256 of `b"dwr-generator-v2\0" + seed_u64be + b"\0" + partition_ascii + b"\0" + candidate_index_u64be`, taking the first eight digest bytes as an unsigned big-endian integer. Record config hash, generator version, Python version and seed derivation. Candidate indices start at zero and increase monotonically within each partition; outcomes remain in index order.

Candidate draw order is fixed:

1. Draw `n` uniformly from 3 through 6 with `randint(3, 6)`.
2. Assign the partition profile by `candidate_index mod number_of_profiles`, using config order `[eq, neq, add_mod]`, `[(eq,neq),(eq,add_mod),(neq,add_mod)]`, and `[(eq,neq,add_mod)]`. This provides deterministic round-robin exposure. Feasibility uses the same balanced 1,000-source proposal as the full corpus (334/333/333 by singleton) and 100 eligible development examples per pair. The later full proposal uses 600 eligible examples per development pair and 600 final examples. When a profile quota is already full, record `profile_quota_full`, consume the index, and draw nothing else.
3. Draw a private witness by `randrange(3)` once for each variable in `v0…v(n-1)` order. The witness is sampled before constraints and never serialized into model input.
4. Enumerate normalized operand tuples in v1 kind and variable order, then retain only tuples whose primitive formula is true on this witness. For each kind, capacity is this witnessed-tuple count. Enumerate totals 2–8 ascending; a count vector has a positive count for every active kind, zero for inactive kinds, sum equal to the total, and each count no greater than witnessed capacity. If no vector exists, reject as `no_witness_feasible_constraint_set`. Otherwise choose uniformly among feasible totals, then uniformly among that total's lexicographically ordered vectors, and use `rng.sample` without replacement per kind in `[eq,neq,add_mod]` order. Sort the combined constraints canonically.
5. Draw given count uniformly from 1 through `n-2`; draw that many distinct variables with `rng.sample` from the ordered variable list; sort selected names and assign their witness values.
6. Construct and validate the ordinary v1 task. Run the independent exhaustive oracle over all `3**n` assignments. Reject unless the task has exactly one solution (`oracle_non_unique`); on acceptance require the deterministic solver to return the identical solution. A disagreement is a fatal correctness error, not a rejection.
7. For every oracle-unique candidate, compute its v1 content, lineage, structure, and hash split before applying eligibility, so unique-content denominators and split closure are reproducible. Apply the partition's prospective eligibility rule below. Deduplicate by content ID before any denominator/quota count; repeated content is logged as `duplicate_content`. Rejected attempts always consume their candidate index.

The balanced profile schedule and witness-first construction are explicit v2 scientific choices. They do not alter the grammar or numeric G2 floors. They replace random profile draws and post-hoc witness rejection because they expose every required primitive stratum under a fixed proposal, construct only constraints satisfied by a private witness, and make eligibility failures/rejection yield measurable. The schedule can still fail its fixed quotas under the existing cap; there is no padding, retry tuning, or result-based parameter search.

## Prospective eligibility and sensitivity

For a unique source task, independently remove each constraint in canonical constraint order using the oracle's internal assignment enumerator. Mark the task `source_sensitive` iff at least one removal increases the solution count from one to at least two. Only sensitive source tasks are accepted. The v1 audit floors remain registered unchanged: at least 25% sensitivity, and at least one sensitive example for every observed source structure signature. In v2 the accepted-corpus floors are intended to be met by construction; feasibility must additionally report sensitivity yield among unique pre-eligibility source-train content groups so that the source filter cannot hide low yield. No sensitivity/yield/structure metrics are computed for source validation/test rows. The equality-triangle structure remains ineligible and must be absent from accepted source train if it cannot meet the criterion.

For a unique mixed task (development or final), it is primary-eligible iff **all** of the following hold: (a) deleting every constraint of each present kind separately raises the solution count from one to at least two; (b) the bipartite factor graph induced by unassigned variables and constraints touching at least one unassigned variable is connected over every unassigned variable; and (c) each present kind appears in that connected graph. Evaluate each counterfactual independently with the exhaustive oracle. These are the existing v1 mixed-eligibility semantics, promoted into the acceptance decision. Keep unique but ineligible candidates in the outcome stream so the eligible-fraction denominator is auditable. For feasibility, the mixed eligibility numerator and denominator are counted only among unique-content development-validation groups; diagnostic-test rows remain opaque. Only eligible mixed examples enter accepted records.

Use stable rejection names: `profile_quota_full`, `no_witness_feasible_constraint_set`, `oracle_non_unique`, `source_insensitive`, `mixed_kind_not_necessary`, `mixed_unknown_factor_disconnected`, `duplicate_content`. A candidate may have exactly one terminal rejection reason, assigned in that order after profile quota handling; preserve counterfactual counts and graph diagnostics for oracle-unique candidates even when rejected. Accepted records include candidate index, partition/profile, task, content/lineage/structure IDs, split, model-input SHA-256, solver statistics, and private witness/solution. Outcomes include every attempted candidate and rejection reason. Replay must reproduce both outcomes and accepted records exactly.

## Numeric gates and one bounded feasibility decision

No v1 numeric G2 floor is lowered, rounded, substituted, or inferred from an empty cohort. The complete-corpus proposal retains, verbatim: 1,000 source, 1,800 development (600/profile), 600 final; 30,000 attempts per partition; at least 100 accepted groups and 12 signatures per partition; source ID train/validation/test minima 100/20/20; 12 source-train signatures; all three kinds in source train; source value fractions at least 0.1 each; at least two given-count values per partition; source sensitivity fraction at least 0.25 and one sensitive example per source signature; for each mixed profile at least 100 primary-eligible groups, 12 eligible signatures, 0.25 eligible fraction, and one eligible example per held-out signature; development validation/diagnostic totals at least 80/20 and per-profile minima 20/5; common-support cells with at least 10 groups in each of the five registered cohorts and at least 80% of each cohort's groups in common cells; one worker, 600 seconds total active generation-plus-audit budget, and 1 GiB resident-memory cap. Preserve all other strata, prompt bins, solver-bin definitions, structural comparisons, audit requirements, and stop-on-cap behavior in `constraint_v2.json` by explicit copy/version, not implicit inheritance.

Run exactly one feasibility attempt after implementation review. Generate the balanced 1,000 unique source groups and continue each development profile until 100 primary-eligible unique groups are assigned to `development_validation`; candidate structure hashes can also place records in source validation/test or `development_diagnostic_test`. Preserve such held-out rows as opaque artifact records needed for deterministic replay, but exclude their counts and all task/eligibility/solver metrics from the feasibility decision; integrity-only replay and hash checks are allowed. Do not generate final groups. Source quota is 1,000 total, not 1,000 source-train groups. The fixed development-validation quota provides 100 groups per pair, above the existing 80-total and 20/profile validation minima and the 100 eligible-group/profile floor; diagnostic candidates are never used to meet that quota. Cap each attempted partition at 30,000 candidates and the single combined generation-plus-independent-audit command at 600 active seconds, 1 GiB, one worker. Use one new unique artifact directory; never overwrite the interrupted v1 run or prior evidence. Record the resolved manifest before work, per-candidate outcomes and hashes. A failure, cap, or no-go is preserved; do not retry with changed rules.

Feasibility passes only if all predeclared floors computable on source **train** and development **validation** pass. These are: at least 100 source-train groups; 12 source-train structure signatures; all three primitive kinds in source train; each solution-value fraction at least 0.1 in source train; at least two given-count values in source train; source sensitivity fraction at least 0.25 and at least one sensitive source-train example per observed source-train signature; development validation at least 80 groups and at least 20 per pair; for every pair, at least 100 primary-eligible groups, 12 eligible signatures, at least 0.25 eligibility among unique-content groups, and at least one eligible example per eligible signature; independent replay; annotation exclusion; and held-out composition absent from source train. Also calculate a clearly labeled **four-cohort proxy** over source train plus the three development-validation pair cohorts using the unchanged 10-groups-per-cell and 80%-mass thresholds. Proxy failure is a no-go, not a substitute for the eventual five-cohort G2 audit and not evidence about final support. Source validation, source test, and development diagnostic-test rows contribute no split counts, strata, acceptance/yield metrics, or common-support inputs to this decision; only their integrity/replay is checked. Final-target data are absent.

The decision is binary and terminal: one attempt meeting every fixed applicable floor advances to the separately manifested complete-corpus stage under the already authorized continuous-work sequence; any failure is a no-go for this proposal. Preserve the failed corpus, rejection ledger and metrics, and leave `todo.md` G2 unchecked. No tuning loop, arbitrary candidate padding, signature-specific sampling, final-target support selection, or favorable-subset reporting is allowed. After a feasibility pass, freeze a clean source/config manifest, generate all three partitions once in a new unique directory, and apply the full unchanged five-cohort G2 audit. Source split floors and the full development diagnostic/test floors are evaluated only in this complete run.

## Operational integrity

Keep atomic JSON replacement fail-fast except for a bounded Windows sharing-only retry: four total replace attempts with delays 0.01, 0.02, and 0.04 seconds. Count all attempts and delays against the same 600-second guard. Retry only errors positively identified as transient Windows sharing/replace conflicts; unrelated errors, non-Windows errors, and the terminal fourth failure propagate with their original type/context. Do not swallow errors or mark a failed write successful. Readers that observe a live manifest must open with compatible sharing or read only after terminal completion; document this for the controller and audit CLI.

The new local RSS probe measured 252 calls and pointer-cache growth from 3 to 271 with RSS from 19,955,712 to 21,958,656 bytes. It confirms retained dynamically created monitoring types in that probe, not the v1 run's growth or lock owner. Define Windows `ctypes` function signatures and the `PROCESS_MEMORY_COUNTERS` structure once at module scope (or one cached initializer) and reuse them. Add a regression asserting repeated resource reads do not grow the relevant type/cache identity count after initialization. Keep the old v1 measurements unchanged; do not claim the monitor issue caused the manifest error.
