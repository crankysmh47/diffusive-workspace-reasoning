# Finite-domain composition task, v2 proposal

Date: 2026-10-08. Status: **registered v2 proposal; one feasibility attempt ended NO-GO at the source attempt cap; G2 not assessed**. The v2 generation/audit implementation and the single registered attempt are recorded in [the v2 execution plan](task_v2_execution_plan.md) and [the suitability result](task_suitability_v2.md). This document versions the task-generation contract after the incomplete v1 attempt; [task_spec.md](task_spec.md), [constraint_v1.json](../configs/tasks/constraint_v1.json), the v1 run, and its partial evidence remain frozen.

## Question and scope

The scientific question remains fixed-N exchangeable transfer: can one workspace/interface trained on source tasks transfer to unseen compositions of the same three known rules, without target-specific tuning? This proposal changes only candidate generation and prospective task eligibility. It does not add diffusion, variable slot count, new model families, or training. A passing task gate is necessary, not sufficient, for any later model comparison.

The v1 partial run stopped at 22,450 of 30,000 source attempts with `PermissionError [WinError 5]`; this was a Windows manifest-replacement interruption, not an exhausted attempt/resource cap. Source yielded 185 accepted groups; development and final were unattempted. Thus there is no measured zero target yield. Of the source structures seen, 51 signatures had no example sensitive to removal of one constraint. The observed n=3 equality triangle is demonstrably redundant under that test: deleting any edge leaves one solution. The old common-support result has empty target cohorts and cannot establish mismatch. These facts are retained unchanged; the generator proposal does not explain the original interruption.

## Frozen semantic and partition contract

The v1 grammar and model boundary remain byte-for-byte authoritative: schema `constraint-task-v1`; modulus 3 and domain `{0,1,2}`; `n` in 3–6; 2–8 distinct-operand constraints; 1–`n-2` givens; `eq`, `neq`, and `add_mod` with their v1 arities, operand symmetries, formulas, strict parser/verifier, independent exhaustive oracle, solver order and difficulty statistics. The prompt projection remains unchanged and contains only rules, task, and fixed answer-format instruction. Witnesses, solutions, identities, split labels, sensitivity evidence, and solver/audit fields are private metadata and must never enter model input.

Composition sets and use remain unchanged: source contains singleton profiles `{eq}`, `{neq}`, `{add_mod}`; development contains the three two-kind profiles; final contains `{eq,neq,add_mod}`. Preserve v1 canonical content/lineage/structure IDs and split hash domains/rules. Source content groups use 80/10/10 train/validation/test; development signatures use 80/20 validation/diagnostic-test, with diagnostic-test reporting-only; final signatures are used only for structural audit and untouched final evaluation after all rules and analysis are frozen. Final-target sampling and metrics are prohibited during the feasibility attempt.

## Versioned generation proposal

Implement as generator/config v2 with the same task schema and a new, explicit generator identity. Use root seed `20261007`; unsigned 64-bit root seed and candidate index; UTF-8/ASCII tokens; standard-library `random.Random`, initialized with `seed(..., version=2)`; no global RNG. For each candidate, derive its seed from SHA-256 of `b"dwr-generator-v2\0" + seed_u64be + b"\0" + partition_ascii + b"\0" + candidate_index_u64be`, taking the first eight digest bytes as an unsigned big-endian integer. Record config hash, generator version, Python version and seed derivation. Candidate indices start at zero and increase monotonically within each partition; outcomes remain in index order.

Candidate draw order is fixed:

1. Draw `n` uniformly from 3 through 6 with `randint(3, 6)`.
2. Assign the partition profile by `candidate_index mod number_of_profiles`, using config order `[eq, neq, add_mod]`, `[(eq,neq),(eq,add_mod),(neq,add_mod)]`, and `[(eq,neq,add_mod)]`. This provides deterministic round-robin exposure. Feasibility uses the same balanced 1,000-source proposal as the full corpus (334/333/333 by singleton) and 100 eligible development examples per pair. The later full proposal uses 600 eligible examples per development pair and 600 final examples. When a profile quota is already full, record `profile_quota_full`, consume the index, and draw nothing else.
3. Draw a private witness by `randrange(3)` once for each variable in `v0…v(n-1)` order. The witness is sampled before constraints and never serialized into model input.
4. Enumerate normalized operand tuples in v1 kind and variable order, then retain only tuples whose primitive formula is true on this witness. For each kind, capacity is this witnessed-tuple count. Enumerate totals 2–8 ascending; a count vector has a positive count for every active kind, zero for inactive kinds, sum equal to the total, and each count no greater than witnessed capacity. If no vector exists, reject as `no_witness_feasible_constraint_set`. Otherwise choose uniformly among feasible totals, then uniformly among that total's lexicographically ordered vectors, and use `rng.sample` without replacement per kind in `[eq,neq,add_mod]` order. Sort the combined constraints canonically.
5. Draw given count uniformly from 1 through `n-2`; draw that many distinct variables with `rng.sample` from the ordered variable list; sort selected names and assign their witness values.
6. Construct and validate the ordinary v1 task. Run the independent exhaustive oracle over all `3**n` assignments. Reject unless the task has exactly one solution (`oracle_non_unique`); on acceptance require the deterministic solver to return the identical solution. A disagreement is a fatal correctness error, not a rejection.
7. For every oracle-unique candidate, compute its v1 content, lineage, structure, and hash split before applying eligibility, so unique-content denominators and split closure are reproducible. The candidate generator computes and returns a private eligibility result but owns no seen set and does not assign terminal stream-level rejection reasons. Rejected attempts always consume their candidate index.

The balanced profile schedule and witness-first construction are explicit v2 scientific choices. They do not alter the grammar or numeric G2 floors. They replace random profile draws and post-hoc witness rejection because they expose every required primitive stratum under a fixed proposal, construct only constraints satisfied by a private witness, and make eligibility failures/rejection yield measurable. The schedule can still fail its fixed quotas under the existing cap; there is no padding, retry tuning, or result-based parameter search.

## Prospective eligibility and sensitivity

For a unique source task, privately remove each constraint in canonical order with the oracle's internal assignment enumerator. Mark it sensitive iff at least one removal raises the solution count from one to at least two. The generator uses this private predicate for source acceptance on every source split. The v1 audit floors remain unchanged: at least 25% sensitivity and at least one sensitive example for every accepted source structure signature. In the complete corpus, compute the sensitivity fraction over all unique-content, oracle-unique source groups across source train/validation/test before eligibility; in feasibility, use only source-train unique-content groups. Apply the one-per-signature floor to signatures represented in accepted source groups; report structures seen only among rejected source candidates separately, without making their absence from the eligible corpus a floor failure. Deterministic private computation on source validation/test is permitted when required for acceptance/replay; held-out aggregate statistics and selection inspection are unavailable to the feasibility decision. The equality-triangle structure remains ineligible and must be absent from accepted source train if it cannot meet the criterion.

For a unique mixed task (development or final), the private predicate marks it primary-eligible iff (a) deleting all constraints of each present kind separately raises the solution count from one to at least two; (b) the bipartite factor graph induced by unassigned variables and constraints touching at least one unassigned variable is connected over every unassigned variable; and (c) each present kind appears in that connected graph. These v1 semantics now guide candidate acceptance. The generator writes the private result in each unique-candidate outcome; it does not own corpus state. For feasibility, retain mixed eligibility numerators and denominators by profile among unique-content, oracle-unique development-validation groups; apply the unchanged 0.25 fraction floor to the combined development-validation partition. In the complete corpus, retain per-profile counts and compute the 0.25 floor separately for each complete mixed partition (development and final), using all unique-content, oracle-unique candidates in that partition before eligibility. Duplicates are excluded from both numerator and denominator. Diagnostic rows are opaque during feasibility. Only eligible mixed examples enter accepted records. The per-signature floor requires at least one eligible example for every signature represented in the accepted eligible groups, plus at least 12 distinct eligible signatures per profile. Report signatures seen only among rejected ineligible candidates separately; they are not in the eligible-signature floor and a structure that cannot meet eligibility does not fail it.

Use stable candidate results for pre-unique failures: `profile_quota_full`, `no_witness_feasible_constraint_set`, and `oracle_non_unique`; and eligibility outcomes: `source_insensitive`, `mixed_kind_not_necessary`, and `mixed_unknown_factor_disconnected`. A pure candidate call is stateless and does not return `duplicate_content`. The orchestrator owns one `seen_content_ids` set for the entire generation run, shared across partitions. For each oracle-unique outcome, compute identities/split, then check this set **before** denominators and eligibility terminalization: if the ID is already present, record `duplicate_content` and count neither numerator nor denominator; otherwise insert it immediately, including when private eligibility is false. Thus the first oracle-unique occurrence owns the content ID even when rejected for eligibility, and any later repeat is a duplicate. Non-unique tasks and quota skips never enter the set. The set is recreated for each run and replay begins from empty state. After deduplication, source candidates terminate as `source_insensitive` when the private source predicate fails. Mixed candidates first terminate as `mixed_kind_not_necessary` if any present kind deletion leaves fewer than two solutions; otherwise terminate as `mixed_unknown_factor_disconnected` if unknown-variable connectivity or connected-graph kind coverage fails; otherwise they are eligible. This fixes reason precedence for candidates failing multiple predicates. Per-profile raw mixed denominators contain each first-seen, unique oracle-unique candidate before eligibility; accepted eligible groups are the numerators. Keep rejected-signature coverage as a separate diagnostic. Accepted records include candidate index, partition/profile, task, content/lineage/structure IDs, split, model-input SHA-256, solver statistics, and private witness/solution. Outcomes include every attempted candidate and exactly one terminal stream reason. Replay must reproduce reason precedence, seen-set insertions, outcomes and accepted records exactly.

## Numeric gates and one bounded feasibility decision

No v1 numeric G2 floor is lowered, rounded, substituted, or inferred from an empty cohort. The complete-corpus proposal retains, verbatim: 1,000 source, 1,800 development (600/profile), 600 final; 30,000 attempts per partition; at least 100 accepted groups and 12 signatures per partition; source ID train/validation/test minima 100/20/20; 12 source-train signatures; all three kinds in source train; source value fractions at least 0.1 each; at least two given-count values per partition; source sensitivity fraction at least 0.25 and one sensitive example per accepted source signature; for each mixed profile at least 100 primary-eligible groups and 12 eligible signatures; 0.25 eligible fraction per mixed partition, measured on unique-content oracle-unique groups before eligibility; at least one eligible example per represented eligible signature; development validation/diagnostic totals at least 80/20 and per-profile minima 20/5; common-support cells with at least 10 groups in each of the five registered cohorts and at least 80% of each cohort's groups in common cells; one worker, 600 seconds total active generation-plus-audit budget, and 1 GiB resident-memory cap. Preserve all other strata, prompt bins, solver-bin definitions, structural comparisons, audit requirements, and stop-on-cap behavior in `constraint_v2.json` by explicit copy/version, not implicit inheritance.

## Operational integrity

Keep atomic JSON replacement fail-fast except for bounded Windows replacement-conflict retries: four total `Path.replace` attempts with delays 0.01, 0.02, and 0.04 seconds for Windows error codes 5, 32, or 33. Code 5 can also mean permanent access denial and does not prove a transient sharing conflict; after the fourth attempt, propagate the error. Writes/open errors, other codes, and all non-Windows errors fail immediately. Delays and attempts naturally count against the monotonic 600-second guard; the caller checks the guard before and after replacement. The existing bounded final metadata-flush accounting boundary remains unchanged. Do not swallow errors or mark a failed write successful. Readers that observe a live manifest must open with compatible sharing or read only after terminal completion; document this for the controller and audit CLI.

The new local RSS probe measured 252 calls and pointer-cache growth from 3 to 271 with RSS from 19,955,712 to 21,958,656 bytes. It confirms retained dynamically created monitoring types in that probe, not the v1 run's growth or lock owner. Define Windows `ctypes` function signatures and the `PROCESS_MEMORY_COUNTERS` structure once at module scope (or one cached initializer) and reuse them. Add a regression asserting repeated resource reads do not grow the relevant type/cache identity count after initialization. Keep the old v1 measurements unchanged; do not claim the monitor issue caused the manifest error.
# Prospective clarification — 2026-10-08

For both the four-cohort feasibility proxy and the five-cohort full common-support comparison, source cohorts contain all independently accepted source groups in the applicable split. “All groups” means all accepted source groups regardless of the mixed-primary predicate; independently verified `source_insensitive` rejected proposals are excluded from common-support cells and mass. Those raw first-seen oracle-unique source proposals remain in the registered sensitivity denominator and raw diagnostics. This interpretation applies identically to EX and IDX comparisons, changes no numeric threshold, and does not alter the generator, eligibility predicates, or split definitions.
