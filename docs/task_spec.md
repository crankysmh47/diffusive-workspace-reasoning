# Finite-domain composition task, v1

Status: frozen CPU task contract, implemented and checked with standard-library correctness tests. A bounded corpus attempt exercised the contract but did not complete; G2 is not assessed and this is not a validated benchmark, confirmatory study, or authorization to train. The audit thresholds below are prospective suitability floors; they do not establish power or a practical effect size. See [the bounded suitability result](task_suitability.md).

## Question and scope

The task tests whether a model can complete small, uniquely solvable finite-domain constraint instances using a fixed set of known rules. The intended later transfer contrast is between source compositions and unseen combinations of the same primitives. It does not test unseen rule semantics, larger task size, cross-family transfer, or variable slot count. Every instance has 3–6 named variables over the fixed domain `{0,1,2}`. This is task-size variation for data diversity, not a registered size-transfer experiment.

The grammar uses exactly three relation kinds:

| `kind` | Arity and meaning | Canonical operand symmetry |
|---|---|---|
| `eq` | `value(a) == value(b)` | `(a,b)` is unordered |
| `neq` | `value(a) != value(b)` | `(a,b)` is unordered |
| `add_mod` | `(value(a) + value(b)) % 3 == value(c)` | first two operands are unordered; result `c` is distinguished |

Every constraint refers to distinct variables. In particular, `add_mod` has three distinct variables. There is no implicit all-different rule, inequality beyond explicit `neq`, arithmetic over integers outside modulo 3, or arbitrary value-label symmetry. Given assignments pin individual variables to values in `{0,1,2}`.

## Immutable Python contract

The first implementation uses only the standard library. Public immutable records are frozen, slotted dataclasses; collections are tuples and enums are string enums:

```python
class RelationKind(str, Enum): EQ = "eq"; NEQ = "neq"; ADD_MOD = "add_mod"
@dataclass(frozen=True, slots=True)
class Constraint: kind: RelationKind; variables: tuple[str, ...]
@dataclass(frozen=True, slots=True)
class GivenAssignment: variable: str; value: int
@dataclass(frozen=True, slots=True)
class ConstraintTask:
    schema_version: str; modulus: int; variables: tuple[str, ...]
    constraints: tuple[Constraint, ...]; givens: tuple[GivenAssignment, ...]
class VerificationReason(str, Enum):
    VALID = "valid"; MALFORMED_JSON = "malformed_json"
    NON_FINITE_CONSTANT = "non_finite_constant"; DUPLICATE_JSON_KEY = "duplicate_json_key"
    WRONG_CONTAINER = "wrong_container"; UNKNOWN_KEY = "unknown_key"
    MISSING_ASSIGNMENT = "missing_assignment"; UNKNOWN_VARIABLE = "unknown_variable"
    MISSING_VARIABLE = "missing_variable"; NON_INTEGER_VALUE = "non_integer_value"
    VALUE_OUT_OF_DOMAIN = "value_out_of_domain"; GIVEN_MISMATCH = "given_mismatch"
    CONSTRAINT_VIOLATION = "constraint_violation"
@dataclass(frozen=True, slots=True)
class VerificationResult: valid: bool; reason: VerificationReason
@dataclass(frozen=True, slots=True)
class Solution: assignments: tuple[tuple[str, int], ...]
@dataclass(frozen=True, slots=True)
class OracleResult:
    solutions: tuple[Solution, ...]; assignments_examined: int
```

These are the immutable records needed by the schema, verifier, and oracle milestone. Later solver and generator modules may define their output records when implemented; no placeholder solver/generator dataclasses are required before then.

`schema_version` is exactly `constraint-task-v1`, `modulus` is exactly integer `3` (Python booleans are rejected despite being integers in Python), and variables are exactly the ordered sequence `v0, …, v(n-1)` for a supported `n` from 3 through 6. A task has 2–8 constraints and 1–`n-2` givens, leaving at least two unassigned variables. Duplicate variable names, repeated givens, duplicate constraints after the operand symmetries above, unknown variables, wrong arity, repeated operands, unsupported sizes, out-of-domain values, and all unknown object keys are hard errors. JSON numbers must be integers, never booleans or floats. `parse_task_json(text) -> ConstraintTask` raises `TaskFormatError(code)` for invalid tasks. Stable codes are `malformed_json`, `duplicate_json_key`, `non_finite_constant`, `wrong_container`, `missing_field`, `unknown_key`, `unsupported_schema_version`, `unsupported_modulus`, `unsupported_size`, `invalid_variable_sequence`, `invalid_kind`, `invalid_arity`, `unknown_variable`, `repeated_operand`, `duplicate_constraint`, `duplicate_given`, `non_integer_value`, `value_out_of_domain`, `invalid_constraint_count`, and `invalid_given_count`. Missing object fields use `missing_field`; a present field with a value of the wrong JSON container type uses `wrong_container`; JSON `NaN` and infinities use `non_finite_constant`.

## Strict serialization and model boundary

Task JSON has exactly these top-level keys and shapes:

```json
{"schema_version":"constraint-task-v1","modulus":3,"variables":["v0","v1","v2"],"constraints":[{"kind":"add_mod","variables":["v0","v1","v2"]},{"kind":"neq","variables":["v0","v1"]}],"givens":[{"variable":"v0","value":1}]}
```

The order of task constraints and givens has no semantic meaning. Parsing accepts either order, rejects duplicate JSON object keys (including duplicate assignment keys), rejects non-finite JSON constants, and rejects unknown keys at every level. `serialize_task(task)` emits UTF-8 JSON with no BOM, compact separators, lexicographically sorted object keys, constraints sorted by their normalized `(kind, operands)` encoding, and givens sorted by variable. The variable list stays in required `v0…v(n-1)` order. `parse_task_json(text) -> ConstraintTask` validates rather than repairing input. The parser and serializer must round-trip to one byte-stable canonical serialization. A `Solution.assignments` tuple is ordered by `v0…v(n-1)`.

`serialize_model_input(task) -> str` emits exactly this JSON object shape: `{"answer_schema":{"additionalProperties":false,"properties":{"assignment":{"additionalProperties":false,"properties":{"v0":{"enum":[0,1,2],"type":"integer"}},"required":["v0"],"type":"object"}},"required":["assignment"],"type":"object"},"instruction":"Return one complete satisfying assignment as JSON.","rules":{"add_mod":"(value(a)+value(b)) % 3 == value(c)","domain":[0,1,2],"eq":"value(a) == value(b)","neq":"value(a) != value(b)"},"task":<canonical task object>}`. Replace the single example property/required name with every declared variable in `v0…v(n-1)` order. The `rules` mapping is fixed and identical for every example; it makes all primitives explicit to the model. Serialize the whole object with UTF-8, no BOM, no trailing newline, `ensure_ascii=False`, `allow_nan=False`, compact separators `(',', ':')`, lexicographically sorted object keys, and the canonical task object defined above. These are the exact bytes hashed as model-input identity. The model input excludes content/structure IDs, split, lineage, candidate index, hidden witness, solution, solver traces/statistics, and audit-only fields. All declared variables are required once and only once, with integer values in `{0,1,2}`; answer object key order is immaterial to verification. The model input never includes a target answer or solver annotation.

The verifier API is `verify_answer(task: ConstraintTask, answer_text: str) -> VerificationResult`. Stable reason strings are `valid`, `malformed_json`, `non_finite_constant`, `duplicate_json_key`, `wrong_container`, `unknown_key`, `missing_assignment`, `unknown_variable`, `missing_variable`, `non_integer_value`, `value_out_of_domain`, `given_mismatch`, and `constraint_violation`. Check in this order: JSON syntax, non-finite constants, duplicate keys; top-level container; unknown top-level keys; missing `assignment`; assignment container; unknown then missing variables; value type; domain; given preservation; each relation. The first failing condition determines the reason. A syntactically valid answer with an unknown assignment key yields `unknown_variable`.

## Solver and independent oracle

The later deterministic reference solver interface is `solve(task: ConstraintTask) -> SolveResult`, where frozen records are `SolverStats(first_solution_nodes: int, uniqueness_nodes: int, uniqueness_solution_count_capped: int)` and `SolveResult(solution: Solution | None, stats: SolverStats)`. These records are introduced with the solver milestone; Task 2 does not scaffold them. The solver searches unassigned variables in `v0…v(n-1)` order, values ascending `0,1,2`, and constraints in canonical serialized order. Partial consistency rejects a relation only when all its operands are assigned and the formula is false; it performs no domain propagation or lookahead. Before either DFS pass, evaluate every constraint whose operands are all fixed by givens. If any is false, return no solution with both node counts zero. Otherwise each pass enters one consistent root node, counted once. A search node is one invocation of DFS on a consistent partial assignment, including root and complete leaves; candidate values rejected before recursive descent are not nodes. `first_solution_nodes` counts nodes in the first-solution pass through first solution or exhaustion. A separate uniqueness pass starts at the root, visits nodes under the same order, and stops after exhaustion or the second solution; `uniqueness_nodes` counts all its nodes and `uniqueness_solution_count_capped` is in `{0,1,2}`. First-solution work and uniqueness-proof work remain separate; difficulty comparisons use first-solution nodes, not uniqueness nodes.

The independent oracle API is `enumerate_solutions(task: ConstraintTask, *, excluded_kinds: tuple[RelationKind, ...] = (), excluded_constraint_indices: tuple[int, ...] = ()) -> OracleResult`. It validates the original external task first. Exclusion indices refer to the task's canonical serialized constraint order; both exclusion tuples reject duplicates, invalid enum values, booleans, and out-of-range indices. The oracle then visits the full Cartesian product in lexicographic assignment order (at most `3^6 = 729` assignments), filters givens, skips any constraint whose kind or index is excluded, and evaluates all remaining primitive formulas inline from their mathematical definitions. `assignments_examined` is exactly `3**len(variables)`, including assignments filtered by givens. Exclusions do not construct or parse a relaxed task, so deleting all constraints or leaving fewer than two constraints is supported. For internal counterfactual fixtures outside the external task schema, `enumerate_assignments(variables: tuple[str, ...], givens: tuple[GivenAssignment, ...], constraints: tuple[Constraint, ...]) -> OracleResult` accepts 3–6 valid variables, zero or more valid givens (including all variables given), and zero or more valid constraints (including no constraints); it checks only primitive shapes/domains and never imposes the external 2-constraint/minimum-unassigned rules. It shares only the oracle's direct formula implementation, not solver, verifier, or generator predicates. Both paths return every satisfying solution, not a count capped at two. Solver/verifier/oracle agreement is required before generation is audited.

## Canonical identities and split assignment

`canonical_content(task) -> str` considers all `n!` variable renamings, rewrites variables to the canonical ordered names, applies only the actual operand symmetries listed above, sorts constraints/givens, serializes canonically, and returns the lexicographically smallest representation. The content ID is `sha256(b"dwr-content-v1" + bytes([0]) + canonical_content_utf8_bytes)`. `bytes([0])` is one NUL byte. Thus variable renaming and constraint/given order do not change the ID. No value relabeling is performed.

`canonical_structure(task) -> str` uses the same exhaustive variable-renaming and relation normalization, but omits all given values while retaining which variables are anchors (the given-variable set after renaming), variable count, and every relation kind and operand position. Its exact canonical payload is compact sorted-key UTF-8 JSON with shape `{"anchors":[...],"constraints":[...],"modulus":3,"variables":[...],"version":"constraint-structure-v1"}`; there is no BOM or trailing newline. The structural signature is `sha256(b"dwr-structure-v1" + bytes([0]) + canonical_structure_utf8_bytes)`. Similarly the content ID is `sha256(b"dwr-content-v1" + bytes([0]) + canonical_content_utf8_bytes)`. `bytes([0])` is one NUL byte, not the two printable characters backslash and zero. This intentionally groups tasks that share a constraint structure and anchor locations despite differing clue values. `n <= 6` makes exhaustive canonicalization bounded and avoids a general graph-canonicalization framework.

The composition partition is fixed before generation and any accuracy inspection, using the set of relation kinds present in a task:

| Partition | Allowed relation-kind set | Use |
|---|---|---|
| Source | exactly one of `{eq}`, `{neq}`, `{add_mod}` | training plus source ID train/validation/test |
| Development composition targets | exactly one of `{eq,neq}`, `{eq,add_mod}`, `{neq,add_mod}` | development-only OOD validation and diagnostic test |
| Final composition targets | exactly `{eq,neq,add_mod}` | untouched final OOD test only |

All instances in a partition, all structural signatures, and all lineage descendants remain in that partition. Source ID assignment is by canonical content/lineage group, with a stable hash bucket of 80% train, 10% validation, and 10% test; this intentionally permits familiar source structures across ID splits while preventing exact content and lineage overlap. The bucket is `int.from_bytes(sha256(b"dwr-id-split-v1" + bytes([0]) + content_id_ascii).digest()[:8], "big") % 100`, with residues 0–79 train, 80–89 validation, 90–99 test. Every primitive kind must have at least one source TRAIN group; source-wide coverage alone does not pass.

Development composition signatures are split by this fixed signature hash: `int.from_bytes(sha256(b"dwr-dev-split-v1" + bytes([0]) + structure_signature_ascii).digest()[:8], "big") % 100`; residues 0–79 are `development_validation`, 80–99 are `development_diagnostic_test`. A signature and all its groups stay together. Only `development_validation` may inform development choices. `development_diagnostic_test` is reporting-only: its examples, metrics, and summaries cannot drive generator, prompt, model, hyperparameter, threshold, or checkpoint choices. Its predeclared minimum group counts are fixed data-suitability gates, not values to retune in response to diagnostic outcomes. Both splits are reserved from model training. The gate requires at least 80 validation and 20 diagnostic-test groups total, plus at least 20 and 5 per each pair profile. Final composition signatures are generated only for structural audit and final test after the spec/implementation and analysis are frozen. They cannot be used for model, prompt, threshold, or hyperparameter choices. A final target inspected during the suitability audit remains an untouched target for model choices; no accuracy/model comparison is run at this gate. The exact output split labels are `source_train`, `source_validation`, `source_test`, `development_validation`, `development_diagnostic_test`, and `final_test`.

This split tests composition reuse at familiar `n` values. It is not random-text splitting, and a source ID split is not a composition holdout. No claim of size/depth, input-symmetry, slot-permutation, or cross-family transfer follows from it.

## Seeded generation and audit contract

The config fixes root seed `20261007`. Candidate partition tokens are exactly ASCII `source`, `development`, and `final`. For each partition/candidate, form seed material by concatenating ASCII `dwr-generator-v1`, one NUL byte (`bytes([0])`), the root seed as unsigned 8-byte big-endian, one NUL byte, the partition token, one NUL byte, and the candidate index as unsigned 8-byte big-endian. The stream seed is the unsigned big-endian integer represented by the first 8 bytes of SHA-256(seed material). Initialize `rng = random.Random()` then call `rng.seed(stream_seed, version=2)`; never use module-global RNG. Python runtime version and config hash are recorded because seeded generation is not asserted cross-version bitwise invariant. Candidate indices are monotonic from zero independently within each partition.

For each candidate, call the local RNG in this order: choose `n` uniformly from 3–6; choose one allowed relation-kind profile uniformly from that partition's configured list order; for a development candidate, check immediately whether its profile quota is already 600. If full, log `profile_quota_full`, consume the candidate index, make no further RNG calls, do not increment accepted counts, and continue with the next index's independent stream. This check follows both the `n` and profile draws, preserving the established candidate RNG order, and precedes all constraint, witness, and given draws. For candidates proceeding, enumerate eligible normalized operand tuples with kind order `[eq, neq, add_mod]`, then variable index order (pairs by `itertools.combinations(v0…v(n-1), 2)`; for `add_mod`, each such unordered addend pair followed by each distinct result variable in variable order); choose uniformly a feasible total constraint count from 2 through 8; enumerate feasible count vectors lexicographically in `[eq, neq, add_mod]` order, with zero for inactive kinds, positive counts for active kinds, the chosen sum, and each count at most that kind's tuple capacity; choose one vector uniformly; use `rng.sample(eligible_tuples, count)` independently in `[eq, neq, add_mod]` order; sort constraints canonically; draw each witness variable with `rng.randrange(3)` in variable order; reject if any relation fails on the witness; choose a clue count uniformly from 1 through `n-2`, then `rng.sample(variable_list, clue_count)` and sort the selected variables before assigning witness values. Feasible totals and vectors are sorted ascending before `rng.choice`. Parse/validate the candidate, enumerate all assignments with the independent oracle, and accept only exactly-one-solution tasks. The witness, solution and annotations are persisted only in generation/audit records outside model input. Rejections consume that candidate index; accepted output order is candidate-index order. Thus each development profile stops at 600 and the development accepted total cannot exceed 1,800. Source and final stop at their configured 1,000 and 600 accepted totals respectively. A duplicate canonical content ID is recorded as a duplicate and does not add an output group; its content group and any descendants inherit the same split. The base lineage ID is `sha256(b"dwr-lineage-v1" + bytes([0]) + content_id_ascii)`. All partitions stop at their configured accepted totals or the independent 30,000-candidate cap; preserve partial results at a cap, mark incomplete, and never silently lower a floor or change the grammar.

The audit writes a small resolved manifest before work: exact command, config SHA-256, source commit/dirty state, Python version, seed derivation, output paths, per-partition attempt counts, wall/CPU time and resource limits. Each accepted task record stores canonical IDs, partition, lineage ID, candidate index, exact task serialization, oracle solution, and first-solution/uniqueness stats. The model-input projection is separately serialized and hashed. Generated datasets and per-example records stay outside Git; only config and aggregate audit report/hash manifests are eligible for version control.

## Prospective suitability gate (not a power calculation)

The generation targets exceed the minimum gate to leave room for ID holdout, per-profile eligibility yield, and overlap cells: source targets 1,000 unique groups to provide roughly 100 source-ID test groups under the fixed 80/10/10 hash; each mixed profile targets 600 unique groups so that a 25% eligibility floor can still supply at least 100 primary groups plus 10-group common-support cells. These are finite audit targets, not precision calculations or guaranteed yields. The configured first audit remains bounded to at most 30,000 candidates per partition (90,000 total), 600 seconds wall time, one CPU worker, and 1 GiB resident memory. Stop immediately at the first cap; preserve partial output and mark the audit incomplete. Do not retry under altered rules within this task. Per partition, the structural gate requires at least 100 accepted unique-content groups and 12 distinct structural signatures; source additionally needs at least 100/20/20 train/validation/test groups and at least 12 source signatures in training. Development validation and diagnostic-test splits need at least 80 and 20 groups total, and at least 20 and 5 per each pair profile. Every primitive must occur in source TRAIN, and every target relation-kind set must match its registered partition.

All accepted tasks must have exactly one oracle solution, at least two unassigned variables, and pass deterministic regeneration on a replay audit. Across each partition, each value `0,1,2` must account for at least 10% of all solution variable-values; at least two different clue counts must occur. Every canonical content ID and every lineage ID must occur in exactly one split, model-input bytes must be invariant to changes in audit-only labels/answers, and model-input fields must contain none of those labels/answers. These are explicit leakage and useful-variation checks, not claims about pretrained-model contamination.

For source singleton cases, ordinary interaction sensitivity is measured by removing each constraint in turn while holding givens fixed; at least one removal must raise the solution count from exactly one to at least two. At least 25% of source accepted groups and one group for every source structural signature must meet this condition.

For a mixed development/final primary-eligible case, remove **all constraints of each present kind in turn**, holding givens fixed. Every such removal must raise the solution count from exactly one to at least two; this establishes that each primitive kind contributes to the unique solution. Also build a bipartite factor graph with one node per unassigned variable and one node per constraint touching at least one unassigned variable; connect a factor to every unassigned variable in that constraint. The graph must be connected, include every unassigned variable, and include at least one factor of every present relation kind. Thus a relation label attached only to fixed anchors cannot stand in for an interacting primitive. Unique mixed cases that fail these checks remain in candidate/audit logs as ineligible and are never silently counted as primary transfer examples.

Each development pair profile and the final triple profile must yield at least 100 primary-eligible unique-content groups, at least 12 distinct structure signatures, and one eligible case per held-out signature; primary-eligible groups must be at least 25% of all accepted unique groups in the corresponding partition. Report, by kind and partition, all removal-to-solution-count results, kind-necessity pass rates, graph connectivity, and accepted/ineligible counts. The following is a positive feasibility witness (not evidence of corpus diversity): `n=5`, givens `v0=0,v4=1`, constraints `eq(v1,v2)`, `add_mod(v2,v3,v4)`, `neq(v1,v0)`, `neq(v3,v0)`. Its unique completion is `v1=v2=v3=2`; removing any one of `eq`, `add_mod`, or `neq` constraints produces at least two completions, and the unassigned-variable factor graph is connected. A negative fixture is `n=6`, givens `v0=0,v4=1,v5=0`, constraints `eq(v0,v5)`, `neq(v1,v0)`, `neq(v3,v0)`, `neq(v1,v3)`, `neq(v2,v0)`, `add_mod(v2,v3,v4)`: it is uniquely solvable, but removing `eq` changes nothing and its eq factor touches no unassigned variable, so it is not primary-eligible. Preserve no-go if yield or diversity misses a floor; do not relax rules.

For every partition and split, the audit reports realized group/signature counts, histograms and min/max ranges for `n`, given count, constraint count, serialized model-input UTF-8 byte length, and first-solution nodes. Prompt-byte bins are fixed as `[0,511]`, `[512,639]`, `[640,767]`, `[768,1023]`, `[1024,+inf)`; node bins are `[1]`, `[2,3]`, `[4,7]`, `[8,15]`, `[16,31]`, `[32,63]`, `[64,+inf)`. When a tokenizer/backbone is later frozen, also report tokenized prompt-length distributions and apply the registered model-input common-support gate using that exact tokenizer. The minimum one source-TRAIN group per primitive is only a structural coverage floor, not evidence that the training mixture provides sufficient exposure to learn that primitive.

Before interpreting any composition contrast, form joint support cells from exact `n`, exact given count, exact constraint count, prompt-byte bin, and first-solution-node bin. A cell is common only if it contains at least 10 independent canonical content groups in source ID test, only primary-eligible groups in `development_validation` for each of the three relation-pair profiles, and only primary-eligible groups in final triple-profile test. Logged ineligible target groups never count toward support or its denominator. At least 80% of each cohort's primary-eligible groups must lie in the union of common cells; source ID test uses all its content groups as its denominator. This five-cohort joint overlap requirement may be restrictive; report realized overlap by cell and cohort without implying it will pass. The development diagnostic-test slice does not enter choices or this support calculation. If this gate fails, a model composition comparison is blocked; report the mismatch and do not retune generation against final outcomes. This is an overlap/suitability rule, not statistical power or effect registration.

Passing this audit is at most a structural G2 suitability result. It does not set a meaningful EX–IDX effect size, establish prospective precision/power, authorize comparative training, or validate a model. A small structural audit may pass while confirmatory precision remains unresolved. Comparative training remains blocked until development-only data, feasibility probes, common support, and a separate study registration provide the missing effect, sample, seed, compute, checkpoint, and stop settings required by v2.2.

## Module map and next checks

Implement modules only when needed, under `dwr/tasks/`: `schema.py` owns records, parsing and canonical task serialization; `verifier.py` owns answer parsing and reason codes; `oracle.py` owns independent exhaustive enumeration; `solver.py` owns deterministic partial-check DFS and statistics; `canonical.py` owns content/structure canonicalization; `generator.py` owns seeded candidate generation and record output; `audit.py` owns manifests, replay/leakage/interaction/variation checks and aggregate suitability reporting. Do not scaffold empty modules. The intended commands are `python -m dwr.tasks.generator --config configs/tasks/constraint_v1.json --out data/constraint-v1` and `python -m dwr.tasks.audit --config configs/tasks/constraint_v1.json --data data/constraint-v1`; both must fail closed on unknown config keys and invalid records.

Before model components, add `unittest` checks for strict unknown/duplicate-key rejection, bool/float/domain/shape errors, each primitive truth table, given preservation, every verifier reason, zero/one/multiple solution counts, solver/oracle agreement, clue preservation, independent oracle implementation, variable-renaming and constraint-order ID invariance, structure identity with values omitted but anchors retained, no value-relabel assumption, deterministic regeneration, lineage/content split closure, model-input annotation exclusion, interaction counterfactuals, and fail-at-cap behavior. Test G2 reporting with both a passing fixture and a fixture that remains a no-go. These correctness checks do not require GPU training; none is implemented or claimed by this specification.
