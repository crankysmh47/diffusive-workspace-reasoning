# Finite-domain composition task, v3 proposal

Date: 2026-10-08. Status: **prospective CPU generation and audit design; no v3 candidates sampled**. This design follows the v2.2 research protocol and keeps the fixed-N exchangeable/indexed transfer question unchanged. The v1 and v2 specifications, configurations, partial data, and the single v2 feasibility attempt remain historical and immutable.

## Question and scope

The study asks whether one shared workspace/interface trained on source tasks transfers to unseen compositions of the same three rules without target-specific tuning. V3 changes the proposal for generating source `neq` tasks and how the existing bounded candidate budget is assigned to unfinished profiles. It preserves the grammar, prompt/answer boundary, split rules, solver and independent oracle, numeric floors, cost caps, and all existing v2 eligibility and audit semantics outside the specified `neq` construction. Every later method must use the same frozen v3 corpus. This is an explicit change to the population represented by the corpus; it is not evidence that the proposal will pass suitability.

No diffusion, posterior encoder, dependency-gated optimization, public dataset, model, or training is in this CPU design. A complete full-corpus G2 PASS is required before fixed-size EX/IDX tensor implementation. Training still requires its separate non-null preregistration.

## Symmetry-aware source `neq` proposal

For a selected source `neq` candidate, use this fixed draw order:

1. Draw `n` uniformly from 4 through 6 inclusive.
2. Draw given count `g` uniformly from 2 through `n-2` inclusive.
3. Uniformly sample `g` distinct variable names from ordered `v0`…`v(n-1)` using the candidate-local RNG, then sort them.
4. Enumerate all `3**n` assignments in lexicographic product order over values `(0,1,2)`. Retain private witnesses that use all three values and whose selected given variables contain at least two distinct values. Select one uniformly with `rng.choice`. If the feasible witness list is empty, return the registered closed rejection `no_neq_witness`.
5. Enumerate normalized binary `neq` operand tuples in the v1 order. Retain tuples satisfied by the chosen witness and touching at least one unknown variable. Let `pool_capacity` be their count. Set `low = 2*(n-g)` and `high = min(8, pool_capacity)`. If `low > high`, return the registered closed rejection `no_feasible_neq_constraint_total`; do not fall back to a different count or proposal.
6. Draw total constraint count uniformly from every integer in `[low, high]`, sample that many distinct tuples uniformly without replacement from the ordered pool, and canonically sort the resulting constraints.
7. Construct the usual task with selected witness values on the givens, run the independent exhaustive oracle over all assignments, and keep the v2 deterministic-solver agreement fatal check. Every oracle-unique first-seen content group retains its private eligibility evidence, including groups later rejected as ineligible.

There are no hidden rejection loops, rigid population templates, padding, target quotas by signature, or changed-rule retries. Preserve outcome rows for every attempted index and the existing duplicate/eligibility reason precedence. An empty feasible pool range is a logged closed failure. The constructive witness does not guarantee uniqueness; the exhaustive oracle remains the only uniqueness decision.

### Necessary conditions for unique all-`neq` completion

These statements apply only to satisfying all-`neq` tasks over exactly three colors. They are necessary, not sufficient, and do not generalize here to mixed constraints.

First, the satisfying witness must use all three values. If it uses only two, any unknown variable (there are at least two because `g <= n-2`) can be recolored to the unused third value: every `neq` neighbor had one of the two used values, so the recoloring remains valid and changes the solution. Second, the givens must contain at least two distinct values. If all givens share one value, swapping the other two colors throughout a satisfying assignment preserves every inequality and every given while producing a different solution.

For each unordered pair of colors `{a,b}`, consider the graph induced by vertices whose satisfying assignment has color `a` or `b`, omitting edges whose two endpoints are both givens. A connected component containing an unknown and no given could have its `a` and `b` colors swapped without affecting any edge to the third color, any unknown-given edge, or any given; that would produce another satisfying completion. Therefore every component containing unknown vertices must contain at least one given. If such a component contains `U` unknown vertices and `G >= 1` givens, connectedness requires at least `U+G-1 >= U` edges, and every retained edge touches an unknown. Sum this lower bound over the three color pairs: each unknown vertex occurs in exactly two pair graphs, while each `neq` edge touching an unknown joins one color pair and is counted once. Thus at least `2u` distinct constraints touch unknowns, where `u=n-g`. This establishes a necessary capacity bound, not a guarantee of uniqueness.

## Eligibility, splits, and denominators

Use the unchanged v2 source sensitivity predicate and mixed-kind necessity/connectivity predicate. Source `neq` tasks failing uniqueness, first-seen deduplication, eligibility, split, or solver checks use the same stream contract and terminal reason precedence as v2 after the candidate proposal returns. Duplicates never enter eligibility denominators; the first oracle-unique occurrence owns the content ID even when it is ineligible. Mixed denominators remain first-seen unique-content oracle-unique candidates before eligibility, separately reported by profile. Held-out artifacts required for replay are retained, but held-out aggregate metrics and solver/eligibility summaries remain unavailable to feasibility choices.

The minimum `2u` pool capacity is a mathematical necessary condition only for unique all-`neq` solutions; it is used to define the candidate's feasible-total range. It does not claim unique solutions, and the oracle remains authoritative. No other sampling path changes beyond v3 stream/profile selection.

## Common-support capacity bound before target sampling

After every source profile quota is complete, replay the complete source outcome prefix and verify that the source partition closes at its registered quota before making this decision. An incomplete or capped source prefix may report a diagnostic top-ten mass, but it cannot trigger `source_support_capacity_bound`: later accepted source-training rows could change the mass. An attempt cap remains the cap result; preserve it with all outcomes and assess this bound as unavailable.

Use only accepted, eligible, unique-content `source_train` records to form the registered `_cell` histogram: `n`, given count, constraint count, UTF-8 model-input byte bin, and first-solution node bin. Use the exact existing `_cell` helper and bins. Exclude source validation/test, rejected/ineligible candidates, raw proposals, and all target data. Sort cells lexicographically for ties; divide each cell count by all accepted source-train groups and sum the mass of the ten most frequent cells (or all available cells when fewer than ten). Empty source train has mass zero and cannot pass.

Each of the three feasibility development-validation pair cohorts requires at least 100 eligible groups, and a common-support cell must contain at least 10 examples from each cohort. Therefore no more than 10 cells can contribute to the existing four-cohort 80%-mass floor. If the source-train top-ten mass is below 0.8, that floor is mathematically impossible for the corpus. Record the diagnostic and reason `source_support_capacity_bound`; stop before drawing development or final candidates. The terminal artifact records source complete, development/final not attempted, global generation incomplete, and the explicit proposal no-go reason. The independent audit must replay/validate source closure and recompute the bound from source records with its own aggregation path. It reports `g2_status: not_assessed`, `proposal_status: NO_GO`, and `proposal_reason: source_support_capacity_bound`; it must not claim an observed source-to-target mismatch or an actual support comparison.

If the bound is at least 0.8, it does not show that support passes. Generate the registered 100 development-validation eligible groups per pair, then compute the unchanged four-cohort proxy with all original floors. A complete feasibility PASS is followed by one full-corpus run only under the same clean source HEAD and exact config identity, with its closed linkage consuming the matching independent `PASS_FEASIBILITY` artifact. The independent full audit must pass every unchanged five-cohort G2 floor before fixed-size EX/IDX tensor implementation becomes eligible to start.

## Alternatives and decision record

| Choice | Alternative | Reason and affected comparison |
| --- | --- | --- |
| Construct symmetry-aware `neq` witnesses and require the proved necessary value/anchor/constraint conditions. | Raise the cap or continue v2's random `neq` witnesses and rejection. | The v2 feasibility attempt already exhausted its fixed source cap. Random witness sampling spends proposals on label symmetries that cannot have a unique completion; the necessary conditions remove those proposals mechanistically. The accepted `neq` distribution changes, so every EX/IDX/control method must use the same frozen v3 source data. This may still fail uniqueness, sensitivity, floors, or support. |
| Allocate candidate indices among profiles still below quota, selecting profile before `n`. | Preserve v2's fixed round-robin schedule with quota-full draws, or increase the cap. | The bounded attempt budget is concentrated on unfinished registered strata without quota-skip indices or idle attempts. This changes the population mix and candidate-index proposal for every profile; all comparators share the same versioned corpus and report the change. |
| Apply the analytical source-train top-ten bound before target sampling. | Generate development/final targets before checking support, or alter cells/quotas until support improves. | The existing four/five-cohort floor is impossible when the source mass capacity is below 0.8, so the bound can stop avoidable target work. A pass remains only a necessary capacity result. A failure is a terminal no-go for this proposal and needs a separately dated design; it does not justify padding, signatures, quotas, bins, or retries. |

V2 source TRAIN spread over many registered cells; repairing `neq` yield need not repair common support. V3 makes no predicted-pass claim and preserves all negative, incomplete, and capped evidence.
